## Decision recorded before implementation

Personal namespace provisioning is deferred for a separate product and
governance discussion. The organization may have too many namespaces if every
activated account receives one automatically.

This execution must not add or enable:

- automatic personal namespace creation;
- default namespace memberships;
- existing-account personal namespace backfill;
- personal namespace naming or collision policy;
- operator settings whose only purpose is personal namespace provisioning.

The CLI namespace manifest and workspace-sync contract remains in scope. It
describes namespaces that already exist and does not create personal
namespaces.

## Security review

### CIA impact and trust boundaries

- **Confidentiality:** browser and CLI bearer/session credentials cross the
  HTTP boundary but must not enter workspace metadata, logs, generated assets,
  or deployment ConfigMaps. GitHub access tokens may be sent only to validated
  HTTPS user/email endpoints with redirects disabled and bounded JSON
  responses. Skill archives remain inside the configured storage/scanner
  boundary; this follow-up adds no external LLM or scanner disclosure.
- **Integrity:** PostgreSQL owns publication, lifecycle, audit, and scan-outbox
  state. The database-to-Redis-to-scanner boundary carries a durable task ID;
  retries, reclaim, and duplicate delivery must not create a second lifecycle
  transition or detach scan evidence from its version. Namespace manifests and
  CLI sync expose only an independently selected published, downloadable
  version even when `latest_version_id` points to an owner preview.
- **Availability:** rate limits bound authentication, publish, search, resolve,
  download, and social aliases and fail closed when their Redis dependency is
  unavailable. Scan delivery uses bounded retries, leases, restart recovery,
  and a terminal `SCAN_FAILED` state with matching execution evidence.

Changed trust boundaries are: browser-selected folders to ZIP upload; CLI
workspace files to authenticated registry APIs; OAuth provider token/userinfo
and GitHub email APIs; PostgreSQL outbox to Redis and the existing scanner; and
operator settings to Compose/K8s runtime configuration. No new principal type,
credential store, personal namespace authority, or external package processor
is introduced.

### Authorization, invariants, and abuse cases

- Anonymous, wrong-scope, non-member, non-manager, disabled-account, and
  hidden/private skill access remains denied at the backend route or repository
  boundary; frontend visibility is not authority.
- Successful, failed, timed-out, retried, reclaimed, or duplicated scan tasks
  leave publication, outbox, version, audit, and execution rows in one
  explainable state. A terminal delivery failure records both `SCAN_FAILED` and
  failed scan-execution evidence.
- Tests cover token replay/state behavior, unsafe OAuth email endpoints and
  response shapes, traversal/duplicate/oversized folder archives, every
  rate-limited route alias for authenticated and anonymous principals,
  namespace visibility changes, Redis refusal/retry, PostgreSQL rollback,
  restart recovery, and duplicate task delivery.
- Remaining accepted boundary: actual Server/Web RISC-V images must pass the
  dedicated GitHub Actions emulation gate after the feature branch is pushed;
  scanner/full-Compose RISC-V support remains a non-goal.

## Confirmed test seams

- Python migration runner and retained PostgreSQL schema upgrade;
- publish workflow transaction commit/rollback behavior;
- scan outbox dispatcher to the existing Redis stream publisher;
- Redis scan consumer idempotency and lifecycle transitions;
- protected FastAPI routes and generated OpenAPI contracts;
- CLI command interface and workspace filesystem behavior;
- browser publish interface at root and `/skillhub` base paths;
- rendered Compose/Kustomize and production image interfaces.

Tests exercise these public seams rather than private helper calls wherever a
real adapter exists.

## Execution order and phase gates

1. Durable scan outbox: migration, atomic intent, dispatch retry/reclaim,
   terminal state, cleanup, consumer idempotency, then full backend tests.
2. Backend/API gaps: manifest, rate-limit settings, subscription eligibility,
   confirmed OAuth/list/legacy-slug gaps, then generated OpenAPI checks.
3. CLI workspace sync: deterministic fingerprints, local/remote/conflict
   behavior, Windows/POSIX paths, root/subpath registry tests.
4. Web: folder ZIP, confirmed auth/UI fixes, complete Russian locale, self-hosted
   fonts, root/subpath tests.
5. Deployment/docs: Python Server/Web RISC-V, UID/GID, settings wiring,
   operator and user docs.
6. Full real-service acceptance and a dated result note with exact commands,
   deviations, and remaining risks.

Each phase must pass its focused tests and end-to-end gate before the next
phase starts. No commit, push, merge, deployment, publication, release, or PR
is authorized by this execution.
