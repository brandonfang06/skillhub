## 4. 執行順序與完成條件

順序：`T0 → T1 → T3（V46）→ T4（V47）→ T2（V48）→ T5 → T6 → T7 → T8 → T9`。
T10 是獨立內容項，未完成不應阻擋核心功能，但交付必須列明差異。
每一個單元先完成最小 failing behavior test，再實作、整合驗證與結果記錄；
不要先做全部 schema 再補全部 UI。編號是工作識別，不是執行順序；掃描
風險最高，但現有 migration runner 是明確 baseline 升級流程，故依
V46→V47→V48 前進。T2 的 timeout/retry 測試設計可先準備，schema 不跳號。

### T0 — 固定基準與開發環境

- 本機對齊已完成。開始實作前重新記錄 HEAD、origin/dev、上游 tag SHA。
- 在新 feature worktree/branch 執行，從當時驗證的 fork dev 出發；本計畫
  和 audit 文件是未提交交付物，必須帶入該 worktree，不能假設 git checkout 會有。
- 讀 `AGENTS.md`、`server-python/AGENTS.md`、`docs/security.md`、maintenance
  workflow 及相關 skills。執行者若改 API，須使用當前 FastAPI generators。
- 使用獨立 PostgreSQL/Redis/MinIO/scanner 和測試資料庫；記錄 ports、Compose
  project、資料卷。驗證現有 V45 升級狀態及現有 outbox/manifest smoke。
- 驗收：baseline 可重現、沒有吸收 stash/prototypes、runtime 全部 healthy。

### T1 — 認證、併發、audit 與發布小缺口

- 修改落點：`server-python/app/auth/`、`publish/package.py`、
  `publish/orchestration.py`、`governance/`、`audit/`、`promotion/`；
  實際 SQL 放對應 repository/query/helper。
- expired/malformed cookie 在上游允許的 public routes 可匿名讀；protected
  route 不降級放行。分別測 session、user token、service token、disabled
  user、revoked token、CSRF，保留 fork service-principal 邊界。
- 相同 provider identity 同時 callback：一個最終身分，不產生孤兒 account
  或重複 membership，保留 global auto-join opt-in；同一 owner 的相同
  namespace/slug/version 併發 publish：成功者單一，衝突者 deterministic
  business error，無額外物件/outbox/audit。上游用 400；本地
  `api/publish.py:302,332` 已有 version conflict 409，本計畫採 409 延續
  fork 契約，明列 adaptation，不能宣稱 HTTP code 完全相同。
- 對具體治理端點注入 audit failure，檢查狀態一併 rollback；已有 JSON
  編碼不重寫，只補引號、換行及惡意字串 regression。
- extension allowlist 已由 `package_extension()` 與設定 normalization 轉小寫；
  上游也是 extension 比對修正，不是新增任意 basename。只補大小寫 regression，
  不擴大允許上傳的檔案類型。
- 驗收：真 PostgreSQL barrier-based 併發測試、公開/私有讀取矩陣及
  approved global promotion download smoke 通過。只把重現的缺口改程式。

### T2 — 掃描可恢復性（最高風險）

- 修改落點：`publish/scan_consumer.py`、`scan_worker.py`、`scan_outbox.py`、
  `publish/scanner_result.py`、`security_audit.py`、`api/security_audit.py`、
  `core/config.py`；新增 feature-owned retry workflow/repository。
- 契約：`POST /api/v1/skills/{skillId}/versions/{versionId}/security-audit/retry`
  由目前狀態/角色決定 retry；v1 bearer 需 `skill:publish`，角色限 skill owner、
  namespace OWNER/ADMIN、SKILL_ADMIN/SUPER_ADMIN。目前上游只宣告 v1 retry，
  不自行擴充 web alias/token policy。SCANNING 且有 active attempt 再次呼叫
  回同一邏輯結果，不另排 task；disabled scanner、missing bundle 拒絕。
  不只用前端按鈕判權，也不允許通過 retry 繞過 review。
- V48 等價 `security_audit.failure_reason`；公開 error 只給可安全顯示的
  分類，不能洩漏底層 provider、路徑、credential。重試建立新的 attempt
  identity，晚到的舊結果不能覆蓋新 attempt。
- 沿用 V44/V45 outbox。version、audit、retry intent 的更新同一 DB
  transaction；double click/concurrent retry 僅一個新 task，rollback 無外送。
- scanner wrapper 保留 Cisco 1.0.2、LiteLLM pin 與本地兩個 backport。
  只處理 /scan、/scan-upload：capacity 預設 1、busy 503/Retry-After、
  client disconnect 不釋放仍運行的 slot、hard timeout 終止 worker 供容器重啟。
  cleanup 僅指定 scanner owned temp root，避免廣域 glob 刪除。
- 對照上游 read=900s、hard=930s、reclaim=960s、unavailable-age=1h；
  以 Python 設定解析和真正 client/worker 執行時間驗證順序，再定部署值。
  Python reclaim 為 `_MS`，不能把 `PT16M` 填進 int 欄位；既有 override 保留。
- 新增 tests：retry auth/CSRF、same-version parallel retry、late old result、
  age-bound unavailable、busy/disconnect、hard timeout subprocess、restart
  recovery。先用 clock injection 測時間，再以短 timeout 真容器驗證。
- 驗收：真 PostgreSQL/Redis/MinIO/scanner 下 publish→fail→retry→scan→review
  完整閉環；長時間故障有終態，公開畫面不洩露 failure detail。

### T4 — 文字評論與 moderation

- 修改落點：`social/rating.py`、新 text-review repository/workflow、
  `api/social.py`/專用 transport、`audit/`；UI 在 `features/social/`。
