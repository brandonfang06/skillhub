# Upstream v0.2.17 Batch 3B: Admin Namespace Mutations

Date: 2026-08-23

## Outcome

The Python backend now owns the nine upstream administrator namespace mutation
routes under `/api/v1/admin/namespaces`. The surface is session-only,
`SUPER_ADMIN`-only, and uses an explicit platform-admin workflow; it does not
fabricate namespace membership or weaken ordinary namespace routes.

Implemented routes:

- add one member and batch-add members;
- update a member role and remove a member;
- transfer ownership;
- freeze, unfreeze, archive, and restore a namespace.

All requests and responses use typed Pydantic contracts. There are no
`/api/web` aliases, generated frontend changes, or schema migrations in this
batch.

## Transaction And Governance Boundaries

- Every admin mutation locks the namespace row with `FOR UPDATE`.
- Ordinary namespace member add/update/remove/transfer and ordinary namespace
  profile update/delete/lifecycle now use the same namespace-first lock order.
  Both ownership-transfer surfaces then lock all membership rows in row order.
  This closes admin-versus-ordinary races without changing ordinary membership
  authorization.
- GLOBAL namespaces are inspectable but immutable.
- Member, role, and ownership changes require an ACTIVE TEAM namespace.
- Direct OWNER addition or role assignment and OWNER removal are rejected.
- New members and ownership recipients must be ACTIVE user accounts; the
  account row is held with `FOR SHARE` for the transaction.
- Duplicate additions map to the stable `alreadyExists` behavior, including
  concurrent attempts.
- Ownership transfer locks all namespace membership rows, requires exactly one
  current OWNER, rejects a same-owner replay, and atomically changes the old
  OWNER to ADMIN and the selected existing member to OWNER.
- Same-role update replay returns the current member without writing another
  audit row.
- Lifecycle transitions are exactly `ACTIVE -> FROZEN`, `FROZEN -> ACTIVE`,
  `ACTIVE|FROZEN -> ARCHIVED`, and `ARCHIVED -> ACTIVE`. Invalid transitions do
  not mutate or audit.
- Lifecycle operations do not change skills, versions, visibility, or review
  state.
- Lifecycle responses are projected inside the same locked transaction as the
  state and audit writes, including stats, permissions, and the actor's real
  membership role. There is no post-commit detail read that can fail after a
  committed mutation or observe a later transition.

## Audit And Batch Semantics

Each successful mutation writes its audit row inside the same database
transaction. Audit failure rolls back the state change. The audit actor is the
actual SUPER_ADMIN principal and the row carries request ID, client IP, user
agent, affected user and old/new role or lifecycle reason. Email is never
included.

The new member actions are:

- `ADD_NAMESPACE_MEMBER`
- `UPDATE_NAMESPACE_MEMBER_ROLE`
- `REMOVE_NAMESPACE_MEMBER`
- `TRANSFER_NAMESPACE_OWNERSHIP`

Existing lifecycle actions are reused. Batch addition performs a shared
namespace preflight, then one transaction and one audit per item. A database or
audit failure rolls back only that item and processing continues; result counts
therefore describe committed rows.

Known domain failures remain quiet. Unexpected database or audit failures log
only the namespace slug, affected user ID, requested role, actor user ID,
request ID, and exception type before returning `UNKNOWN_ERROR`; exception
text, email, token, and secret values are not logged.

## TDD And Real PostgreSQL Evidence

The first route test run failed with the nine mutation routes absent. A later
real-PostgreSQL test proved GLOBAL validation happened before the namespace
lock and returned the OWNER-role error; validation moved inside the locked
transaction so GLOBAL immutability wins. Another RED test showed that an audit
failure escaped batch processing and stopped later items; the per-item boundary
now records that item as failed after rollback and continues.

Real PostgreSQL race coverage proves:

- two concurrent duplicate additions yield one committed membership and one
  `alreadyExists` loser, with one audit;
- two concurrent same-recipient ownership transfers yield one success and one
  same-owner loser while preserving exactly one OWNER and one transfer audit;
- two concurrent freezes yield one FROZEN state, one invalid-transition loser,
  and one lifecycle audit;
- admin and ordinary competing ownership transfers serialize and preserve
  exactly one OWNER; admin role/remove races against ordinary transfer cannot
  leave zero or multiple owners, and only successful admin operations audit;
- admin freeze waits behind an in-flight ordinary profile update, while
  ordinary unfreeze completes before a competing admin archive, preventing
  stale authorization/state decisions from overwriting governance state;
- a deliberately paused lifecycle response projection holds the namespace lock,
  returns the transition's own status, and prevents a later transition from
  changing the response;
- audit injection failure rolls back both membership and lifecycle mutations;
- zero or multiple current owners reject transfer without audit;
- batch partial success remains durable per item.

All PostgreSQL fixtures use full UUID-derived user IDs, namespace slugs, and
search terms so parallel reviewer and test processes cannot select or delete
one another's data.
