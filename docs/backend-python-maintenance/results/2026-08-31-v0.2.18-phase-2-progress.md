## Security review

The change crosses three existing trust boundaries: the authenticated publish
workflow into PostgreSQL, the background dispatcher from PostgreSQL into
Redis, and the Redis consumer into the scanner workflow. It does not add a new
credential, public endpoint, external scanner, LLM, or package-content export.

- **Confidentiality:** the outbox stores only existing scan-routing fields and
  request correlation metadata. Tests and logs do not include database or
  Redis credentials, authorization headers, package contents, or private
  findings. Sent rows have bounded retention.
- **Integrity:** the audit row and unique task intent commit atomically with
  the version. Optimistic entity versions and leases prevent two dispatchers
  from completing the same claim. The consumer rejects a completed `task_id`
  before acquiring a version lease. Rollback, replacement, version deletion,
  and hard deletion leave no dispatchable stale intent.
- **Availability:** Redis failure no longer rejects the publish request or
  loses the scan intent. Retry delay is bounded exponential backoff, expired
  leases are reclaimable, attempts are bounded, and terminal delivery failure
  changes a still-scanning version to `SCAN_FAILED` rather than leaving it
  stuck indefinitely.

Verified failure invariants include transaction rollback, real Redis
connection refusal, restart recovery, expired leases, maximum attempts,
duplicate task delivery, and retention cleanup. PostgreSQL remains the source
of truth for pending delivery. Redis is an asynchronous delivery boundary,
not part of the publish transaction.
