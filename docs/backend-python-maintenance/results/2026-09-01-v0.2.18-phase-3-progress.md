## Scope decision retained

Personal namespace provisioning remains deferred. This phase does not create
personal namespaces, add default memberships, backfill accounts, choose a
naming or collision policy, or expose a setting that enables those behaviors.
The namespace manifest is read-only and reports only an already-existing
namespace that the caller may access.

## Completed implementation

### CLI namespace manifest

- Added `GET /api/cli/v1/namespaces/{namespace}/skills` for existing
  namespaces.
- Supports session and bearer authentication. Bearer tokens require
  `skill:read`.
- Filters out inactive, hidden, inaccessible, or non-installable skills and
  emits stable paging plus content fingerprints.
- Uses PostgreSQL authorization and does not create or mutate namespaces,
  memberships, skills, or versions.

### Configurable rate limiting

- Added an opt-in Redis sliding-window limiter for authentication, publish,
  search, skill, and download categories.
- Identities and download resource coordinates are SHA-256 hashed before they
  become Redis keys.
- Per-category authenticated, anonymous, and window overrides are parsed from
  configuration.
- The default remains disabled for backward compatibility. The disabled path
  does not initialize Redis or load unrelated deployment settings.
- When enabled, a Redis failure fails closed with `503` and `Retry-After`.
  Exhaustion returns `429`; a protected route configured with an anonymous
  limit of zero preserves the route's `401` authentication semantics.

### Subscription authorization

- New subscriptions now use the same visibility, namespace membership,
  account status, hidden-state, latest-version, and namespace-status policy as
  subscription metadata reads.
- Publication recipient selection rechecks those facts inside the publication
  transaction before persisting a subscriber notification.
- Stale subscription rows are retained as relationship history; they do not
  grant current read or notification authority.

### List projections and compatibility reads

- Web and v1 skill lists accept optional `include=labels`, including repeated
  and comma-separated values. Unknown projections fail before the search.
- Labels are loaded with one bounded batch query and locale fallback only when
  requested.
- Search and social list responses now project the skill owner identifier and
  owner display name from a joined user row.
- Legacy plain-slug resolution now prefers public skills, then the global
  namespace, then the lowest skill id while retaining active, visible, and
  published-version eligibility.

### OAuth identity hardening

- Generic OIDC email claims are trusted only when `email_verified` is exactly
  true.
- GitHub login reads the configurable email API and selects a primary verified
  address before another verified address. Provider email lookup failure does
  not abort login, but the unverified profile email is not persisted.
- Unverified login data preserves an existing local email rather than
  overwriting it.
- Merged and system accounts are rejected before profile mutation or identity
  binding.

### Package and generated API contracts

- ZIP directory entries ending in either `/` or `\\` are treated as
  directories on every host OS. This is an adapted Python regression fix: the
  prior implementation depended on the host path separator and therefore did
  not fully satisfy the planned already-covered classification.
- The frontend generator now reads FastAPI `/openapi.json`, not the removed
  Java `/v3/api-docs` endpoint.
- Added Python schema-only compatibility components for the response and
  request types narrowed by `web/src/api/types.ts`. No dummy endpoint or Java
  runtime compatibility layer was added.
- Token OpenAPI paths preserve the established `{id}` parameter name without
  changing their wire URLs.
- Regenerated `web/src/api/generated/schema.d.ts` from the running Python
  backend. The large generated diff replaces the stale Java document with the
  actual FastAPI route set.

## Security review

The phase exercises existing trust boundaries between browser or CLI clients,
FastAPI authentication, PostgreSQL authorization data, Redis counters, and
OAuth providers. GitHub's verified-email endpoint is an additional provider
read within the existing OAuth trust boundary; it is not a new login method.

- **Confidentiality:** manifest and subscriber data are filtered with current
  visibility and membership facts. Rate-limit keys do not expose user ids, IP
  addresses, skill coordinates, tokens, or credentials. Unverified provider
  email data is not persisted.
- **Integrity:** the manifest is read-only. Subscriber eligibility is checked
  in the same transaction that writes publication outcomes. Merged and system
  account guards run before OAuth profile changes. Generated OpenAPI now comes
  from the production Python application rather than a retired runtime.
- **Availability:** list projections are opt-in and batched, page sizes remain
  bounded, and Redis rate limiting is disabled by default. When operators
  enable it, dependency failure is explicit and fail-closed rather than an
  unbounded bypass. OAuth provider email lookup failure continues login
  without trusting the unavailable claim.

Security verification covers anonymous and authenticated rate-limit keys,
limits, exhaustion, unavailable Redis, protected-route authentication,
private and namespace-only subscription authorization, publication-time
recipient rechecks, verified and unverified OAuth email claims, merged/system
accounts, and PostgreSQL-backed identity behavior.
