## Projection Contract

- Version list and version detail responses add nullable
  `complianceSnapshot` fields read only from the immutable version row's
  `parsed_metadata_json.complianceSnapshot` value.
- Portal search `SkillSummary` responses project the snapshot from the exact
  published headline version selected by the existing visibility and fallback
  query. `SkillDetailResponse` remains unchanged, matching upstream v0.2.17.
- Review skill detail adds the snapshot to each version, so the frontend can
  compare the normalized immutable declarations of the reviewed and prior
  versions.
- Historical rows with absent, invalid JSON, non-object metadata, or a
  non-object snapshot project `null`. Malformed mapping/evidence array entries
  are skipped, matching the tolerant upstream response projection.
- Owned and social-list `SkillSummary` responses expose the additive field as
  `null`, matching the upstream profile-list contract rather than guessing a
  mutable or unresolved version.

The Python routes in this area use dictionary response envelopes rather than
Pydantic response models, so no generated frontend file was manually edited in
this backend-only checkpoint.

## Search Safety Adaptation

Both full rebuild and per-skill incremental refresh still select the existing
published fallback version with files. Search keywords and text now include
only normalized compliance mapping `standard`, `version`, `controlId`, and
`title` values.

The raw frontmatter field `x-astron-compliance` is reserved and never flattened.
Evidence `type`, `path`, `url`, and `sha256`, snapshot digests, and malformed
nested values are not indexed. Existing visibility, namespace, label, title,
and lifecycle filters are unchanged.

## Projection Payload And Pagination Hardening

A subsequent quality review found that the first projection query still read
the complete `parsed_metadata_json` document before extracting the snapshot,
and that version-list pagination occurred in Python after all visible rows had
been loaded. It also identified Python's legal-JSON integer digit-limit
`ValueError` as an unhandled parser boundary.

Tests were added before the correction. The RED run reported:

```text
9 failed, 2 passed in 1.80s
```

Version list and review queries now select only the JSONB
`complianceSnapshot` member. Search uses a metadata-free published-version
LATERAL join for its count and a snapshot-only LATERAL projection for the
returned page. No list, review, or search projection transfers unrelated
frontmatter or the full parsed metadata document.

Version listing now performs a separate status-filtered count and applies its
existing lifecycle ordering with `LIMIT` and `OFFSET` in PostgreSQL before the
snapshot is returned. Access checks, visible-status rules, ordering, total,
and zero-based pagination remain unchanged.

Both projection and search metadata parsers now treat `TypeError` and
`ValueError` as malformed historical data. A legal JSON document containing an
integer beyond Python's configured digit conversion limit therefore projects
`null` or contributes no search fields instead of raising.
