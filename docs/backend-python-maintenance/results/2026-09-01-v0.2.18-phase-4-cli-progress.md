## Scope decision retained

Personal namespace provisioning remains deferred. The CLI synchronizes only a
namespace that already exists. It does not create namespaces, add memberships,
backfill accounts, or choose personal namespace names.

The package remains at CLI version `0.1.9`. This phase does not publish, tag,
or release `0.1.10`.

## Completed implementation

### Workspace synchronization

- Added `sync pull`, `sync status`, `sync diff`, and `sync push`.
- Pull pages through the authenticated read-only namespace manifest and stores
  per-skill and workspace sync metadata under `.skillhub/`.
- Status distinguishes `not-installed`, `up-to-date`, `update-available`,
  `local-changed`, and `orphaned` entries.
- Pull preserves changed and unmanaged directories. `--force` is required to
  replace local changes, while `--prune` removes only unchanged managed
  orphans unless `--force` is also explicit.
- Push accepts one directory or `--all`, supports dry-run and review
  submission, and continues reporting other entries after one failure.

### Content and filesystem integrity

- Implemented the same aggregate SHA-256 fingerprint contract as the Python
  manifest: normalized sorted paths plus each file SHA-256.
- Pulled archives are extracted and fingerprinted before an old directory is
  moved. A manifest mismatch aborts the install and preserves the prior
  directory and inventory.
- `.skillhub` metadata is excluded from fingerprints and uploaded ZIPs.
- ZIP entry names use `/` on Windows and POSIX hosts.
- Existing transactional multi-target install, canonical-path preflight,
  backup, inventory rollback, and stale-record cleanup remain intact; the
  simpler upstream install replacement was not copied over them.
- Pagination rejects a repeated opaque cursor rather than looping forever.

### API contract adaptations

- Publish validation and publish accept `rejectExistingVersion=true`.
- Strict validation rejects any existing owned version, including uploaded,
  pending-review, rejected, or published states.
- Strict publish has an independent pre-write replacement guard.
- Publish responses include the actual persisted version status so the CLI can
  decide whether review is already pending or must be submitted.
- The Python v1 submit-review route now accepts bearer authentication and
  requires `skill:publish`; the prior route discarded `Authorization`, which
  made the upstream CLI workflow return `401` after upload.
- Registry base paths are retained and manifest namespace/cursor values are
  encoded.

### Documentation and generated contract

- Updated CLI help, root quick start, CLI metadata examples, workspace safety
  behavior, token scopes, and the command reference.
- Regenerated the frontend API schema from the running FastAPI
  `/openapi.json`; it now includes strict publish form fields and the publish
  status response.

## Security review

- **Confidentiality:** API tokens remain in user credential storage or process
  environment and are never written to workspace sync metadata. `.skillhub`
  metadata is excluded from uploads. Manifest reads continue to use backend
  visibility and membership authorization.
- **Integrity:** downloaded content must match the server manifest before
  replacement. Local changes, unmanaged directories, and changed orphans have
  explicit overwrite/delete gates. Push cannot silently replace any existing
  version. Review submission requires `skill:publish`.
- **Availability:** manifest pages remain bounded at 100 entries, repeated
  cursors terminate with an error, and per-skill push failures do not stop the
  remaining `--all` entries. Filesystem and inventory rollback preserve the
  last usable installation after failed extraction, verification, or commit.

The changed trust boundaries are the authenticated CLI-to-FastAPI manifest,
publish, download, and submit-review calls plus the downloaded archive entering
the local workspace. No new external service, namespace authority, or hybrid
runtime was introduced.

### Real-service CLI smoke

FastAPI ran on `127.0.0.1:8080` with the dedicated loopback-only PostgreSQL
(`127.0.0.1:57632`) and Redis (`127.0.0.1:57679`) services. Both scan daemons
were disabled for this CLI contract smoke.

Using a locally registered test account and a `skill:read` plus
`skill:publish` token, the real CLI verified:

1. `whoami` resolved the bearer principal;
2. `sync status` reported the built-in skill as `not-installed`;
3. `sync pull` downloaded it and verified its fingerprint;
4. the next status reported `up-to-date`;
5. public push returned `PENDING_REVIEW` and `submitted-review`;
6. a duplicate strict dry-run exited `6` with
   `Version already exists: 2.0.0`;
7. private push returned `UPLOADED`; and
8. a real bearer-authenticated submit-review call reached `PENDING_REVIEW`.

The temporary workspace was removed after a resolved-path containment check.
The one exact smoke inventory target accidentally written to the normal user
inventory during the first run was identified and removed without touching
other entries. The test account and versions remain only in the dedicated
Phase 2 PostgreSQL container for later acceptance checks.

## Deviations from upstream

- Preserved the fork's stronger atomic multi-target installer instead of
  replacing it with upstream's simpler per-target flow.
- Added post-download manifest fingerprint enforcement and repeated-cursor
  protection beyond the upstream v0.2.18 implementation.
- Adapted strict publish and response status to the Python backend because the
  upstream Java publish response did not implement the assumptions made by the
  upstream CLI sync code.
- Added v1 bearer submit-review scope enforcement required by this Python
  authentication architecture.
