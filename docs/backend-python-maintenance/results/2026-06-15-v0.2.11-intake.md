## Method Note

For a language rewrite that still follows an upstream project, the reliable
process is:

1. Use upstream tag-to-tag Git diff as the source of truth.
2. Treat release notes and commit messages as orientation only.
3. Classify each change by contract type: API, schema, auth/security, storage,
   background jobs, frontend expectation, docs, CI, or observability.
4. Write parity tests in the new implementation before or alongside each port.
5. Keep an intake/result note so later sync work can audit why a change was
   ported, skipped, or deferred.

This avoids copying removed behavior and keeps the Python branch aligned to the
final upstream release contract instead of transient commits.
