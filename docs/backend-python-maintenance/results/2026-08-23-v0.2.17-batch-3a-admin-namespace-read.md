# Upstream v0.2.17 Batch 3A: Admin Namespace Read Surface

Date: 2026-08-23

## Outcome

The Python backend now owns the four upstream administrator namespace read
routes under `/api/v1/admin/namespaces`. The surface is session-only and
`SUPER_ADMIN`-only. It does not add `/api/web` aliases, mutations, frontend
artifacts, schema changes, or implicit namespace memberships.

## Implemented Surface

- `GET /api/v1/admin/namespaces`
- `GET /api/v1/admin/namespaces/{slug}`
- `GET /api/v1/admin/namespaces/{slug}/members`
- `GET /api/v1/admin/namespaces/{slug}/member-candidates`

All four routes use typed Pydantic envelopes and Java-compatible camel-case
fields. They share the established administrator authentication policy:

- browser session or local mock current user plus `SUPER_ADMIN`: allowed;
- unauthenticated or invalid bearer: `401`;
- authenticated non-`SUPER_ADMIN`: `403`;
- valid API-token bearer: `403 error.apiToken.endpoint.unsupported`. Bearer
  scheme matching is case-insensitive, consistent with the shared resolver.

## Read-Model Decisions

- Keyword filtering is case-insensitive across slug, display name, and
  description.
- Status and type filters normalize case and reject unknown values with `400`.
- Pages clamp to zero. List/member sizes default to 20 when non-positive and
  cap at 100. Pages above Java's signed-int maximum (`2147483647`) return a
  controlled `400`; the maximum itself remains valid and its derived OFFSET is
  safe in PostgreSQL `bigint`. Candidate size defaults to 10 and caps at 20.
- Namespace list ordering is `updated_at DESC, slug ASC`.
- Top-level lifecycle stats are unfiltered.
- `memberCount` includes every membership and `skillCount` includes every skill
  container. These values intentionally differ from eligible-catalog Namespace
  Analytics counts.
- The list query bulk-loads page counts and the real actor membership role. It
  does not perform per-row application queries and never fabricates a role for
  a platform administrator.
- GLOBAL is inspectable and immutable. TEAM capability flags match the approved
  ACTIVE/FROZEN/ARCHIVED matrix.
- Member listing can inspect any namespace without namespace membership.
- Candidate search requires a mutable ACTIVE TEAM namespace, searches ACTIVE
  accounts only, and uses SQL `NOT EXISTS` against all current memberships.
- Existing ordinary namespace routes retain their membership checks.

## TDD Evidence

The first focused run failed during collection because
`app.admin_namespace` did not exist. A later real-PostgreSQL regression test
failed because a one-character GLOBAL candidate search returned `tooShort`
before `immutable`; validation order was then corrected to match upstream.

Quality follow-up tests also proved two boundary failures before their fixes:

- lower-case and upper-case bearer schemes bypassed the shared administrator
  API-token rejection and allowed a valid SUPER_ADMIN token through;
- pages above Java's signed-int maximum were not rejected before OFFSET
  calculation and database binding.

The administrator policy now delegates bearer detection to the same
case-insensitive helper as the auth resolver. Cross-admin tests cover this new
namespace route and the existing admin-user route for valid and invalid tokens.
Page normalization rejects only values above `2147483647`, remains negative-to-
zero compatible, and is caught inside both HTTP route error boundaries.

The real-PostgreSQL fixture seeds ACTIVE, FROZEN, and ARCHIVED TEAM namespaces,
an unassociated platform administrator, mixed lifecycle skill containers,
members, candidates, a published version, and a file. It proves:

- a non-member platform administrator can inspect TEAM and GLOBAL namespaces;
- management `skillCount` reports three containers while Namespace Analytics
  reports one eligible catalog skill;
- existing and inactive accounts are absent from candidate results;
- member counts include all memberships;
- ordinary non-member namespace detail remains forbidden.
