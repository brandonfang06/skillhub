# Service Principal Authentication For OSS Source Import

Status: approved for implementation on 2026-08-18.

## Problem

The OSS GitHub source importer currently accepts an ordinary SkillHub API token.
Although the GitLab job separately sends the triggering person's Keycloak
`preferred_username`, the bearer credential still resolves through
`api_token.user_id` and inherits that user's platform roles. This makes a human
account appear to execute the import and suggests that each pipeline trigger
must provide a personal SkillHub token.

GitLab needs one centrally managed machine credential. A Platform Admin creates
and rotates that credential, while the triggering person's preferred username
is separate attribution data. The service executing the request must never be
confused with the person who owns or submits the imported skill.

## Goals

- Model GitLab import automation as a first-class service principal.
- Let a `SUPER_ADMIN` create, rotate, revoke, and disable service credentials.
- Keep the service credential independent from the administrator who created it.
- Authenticate OSS source imports only with a dedicated service token.
- Preserve the existing preferred-username attribution and namespace-owner fallback.
- Record the service actor and human attribution separately and queryably.
- Keep existing user API tokens, CLI behavior, OAuth sessions, scanner, review,
  storage, and subpath routing behavior unchanged.
- Provide an admin UI and Chinese operating procedure for the complete lifecycle.

## Non-Goals

- Generic service credentials for arbitrary SkillHub APIs.
- OAuth client-credentials, GitLab OIDC/JWT federation, or external secret-manager integration.
- Allowing a service principal to own a namespace or skill, join a namespace,
  submit a review as a user, or approve a review.
- Auto-publishing imported content or bypassing scanner and namespace-owner review.
- Deleting service principals or rewriting historical import/audit records.
- Supporting Git providers other than public HTTPS GitHub repositories.

## Terminology

- **Service principal:** a non-human SkillHub identity representing one automation,
  such as `gitlab-oss-importer`.
- **Service token:** a hashed, revocable credential owned by a service principal.
  It is transported with the HTTP Bearer scheme but is not a user API token.
- **Token creator:** the Platform Admin who created or rotated a service token.
  Creator identity is audit metadata and grants no runtime identity to the token.
- **Service actor:** the service principal authenticated for the import request.
- **Pipeline initiator:** the Keycloak preferred username supplied by GitLab.
- **Attribution user:** the active SkillHub user resolved from the initiator, or
  the current namespace owner when no binding exists.
- **Stable skill owner:** the attribution user for a new source skill and the
  existing owner for every later version.
- **Review submitter:** the attribution user for the current import operation.

## Architecture And Isolation

Service credentials use separate `service_principal` and `service_token` tables.
They do not reuse `api_token`, `user_account`, user role bindings, account merge,
or device authorization. User tokens retain the `sk_` prefix and all existing
behavior. Service tokens use an `st_` prefix.

The generic user bearer resolver remains user-only. A dedicated service-token
resolver is called only by the OSS source-import routes. Other SkillHub routes do
not attempt to resolve `st_` tokens and reject them as unsupported credentials.
This makes it impossible to expand a service token's reach merely by adding a
scope string.

The source-import route requires both:

- an ACTIVE service principal with a valid, unexpired, non-revoked token; and
- the exact token scope `source:import`.

It no longer checks `SKILL_ADMIN` or `SUPER_ADMIN` user roles because no user is
authenticated. Only a logged-in `SUPER_ADMIN` can manage service principals and
their tokens.

## Data Model

### `service_principal`

| Column | Contract |
| --- | --- |
| `id` | UUID/string primary key generated by SkillHub |
| `code` | unique immutable lowercase slug, for example `gitlab-oss-importer` |
| `display_name` | mutable human-readable name |
| `status` | `ACTIVE` or `DISABLED` |
| `created_by_user_id` | required FK to the creating admin |
| `created_at`, `updated_at` | timestamptz |

Principals cannot be deleted. Disabling one immediately blocks every token while
preserving audit history. Re-enabling restores only tokens that are otherwise
valid and not revoked.

### `service_token`

| Column | Contract |
| --- | --- |
| `id` | bigint primary key |
| `service_principal_id` | required FK |
| `name` | unique, case-insensitive among active tokens for one principal |
| `token_prefix` | display-safe prefix |
| `token_hash` | globally unique SHA-256 hash; raw token is never stored |
| `scope_json` | allowlisted scopes; MVP permits only `source:import` |
| `created_by_user_id` | required FK to the admin who created/rotated it |
| `created_at`, `expires_at` | timestamptz; expiry is required and at most 365 days |
| `last_used_at`, `revoked_at` | nullable timestamptz |

Raw tokens start with `st_`, contain cryptographically secure random material,
and are returned exactly once. Token list endpoints return only metadata.

Rotation is atomic: create a replacement token, revoke the selected old token,
and return the new raw value in one transaction. If replacement creation fails,
the old token remains valid.

### Import provenance and audit

`audit_log` gains nullable `actor_service_principal_id`. Existing user audit
writes continue using `actor_user_id` unchanged. Service-import audit writes set
the service field and leave the user actor null. Admin audit responses expose an
actor discriminated union with `actorType=USER|SERVICE` and a display label.

The local OSS source tables keep user foreign keys for the human attribution:

- namespace-source `created_by` is the configured fallback owner used to create
  the namespace;
- skill-source `created_by` is the attribution user for the first import;
- version-source `imported_by` is the attribution user for that version.

They gain explicit service-principal foreign keys for the machine that executed
the mutation. Historical rows remain valid with null service-principal fields.

Each import audit detail records:

- service principal id and code;
- supplied initiator provider and login name;
- resolved attribution user id;
- `attributionSource=INITIATOR|NAMESPACE_OWNER_FALLBACK`;
- stable owner and review submitter ids;
- repository URL, immutable commit SHA, source path, pipeline/job ids when supplied;
- request id, outcome, client address, and user agent.

The admin who created a token is discoverable through `service_token.created_by_user_id`
and is not copied into each import event.

## Platform Admin API

All management endpoints use the existing authenticated browser/session path,
reject bearer API tokens and service tokens, and require `SUPER_ADMIN`.

```text
GET    /api/v1/admin/service-principals
POST   /api/v1/admin/service-principals
PATCH  /api/v1/admin/service-principals/{principalId}
GET    /api/v1/admin/service-principals/{principalId}/tokens
POST   /api/v1/admin/service-principals/{principalId}/tokens
POST   /api/v1/admin/service-principals/{principalId}/tokens/{tokenId}/rotate
DELETE /api/v1/admin/service-principals/{principalId}/tokens/{tokenId}
```

Create-principal request:

```json
{
  "code": "gitlab-oss-importer",
  "displayName": "GitLab OSS Importer"
}
```

Patch-principal request accepts either a new display name or status. Code is
immutable. A disabled principal may still be listed and inspected.

Create/rotate-token request:

```json
{
  "name": "production-gitlab",
  "scopes": ["source:import"],
  "expiresAt": "2027-02-18T00:00:00Z"
}
```

Create and rotate responses include `token` exactly once. List responses never
include it. Delete is an idempotent soft revoke and returns 204.

Validation rules:

- principal code follows lowercase slug rules and is immutable;
- principal display name and token name are nonblank and bounded;
- expiry must be in the future and no more than 365 days from creation;
- unsupported or missing scopes fail with 400;
- duplicate active principal code or token name returns 409;
- missing resources return 404;
- only ACTIVE principals may create or rotate tokens.

Every create, rename, enable, disable, token create, rotate, and revoke operation
writes an ordinary user-actor admin audit event.

## Platform Admin UI

Add `/admin/service-principals` and an admin-menu item named **Service Accounts**.
The page shows service code, display name, status, active-token count, nearest
expiry, last used time, and actions.

The page supports:

- create service principal;
- rename, disable, and enable;
- list token metadata;
- create token with expiry;
- rotate or revoke a token;
- one-time secret dialog with copy button and an explicit warning that the raw
  token cannot be displayed again.

The UI never persists the raw token in query cache or browser storage. Closing
the one-time dialog discards it. Destructive-looking actions require explicit
confirmation, but principals and audit evidence are never deleted.

## Source Import Contract

Existing route paths and import metadata remain stable. Authentication changes:

- valid `st_` service token with `source:import`: accepted;
- missing/invalid/expired/revoked token: 401;
- disabled service principal or missing scope: 403;
- valid `sk_` user token: 403 `error.sourceImport.serviceToken.required`;
- valid service token used on another endpoint: rejected by that endpoint.

GitLab configuration uses:

```text
SKILLHUB_SERVICE_TOKEN
SKILLHUB_IMPORT_TRIGGER_PROVIDER_CODE=keycloak
SKILLHUB_IMPORT_TRIGGER_LOGIN_NAME=<preferred_username>
```

`SKILLHUB_API_TOKEN` is no longer accepted by the importer configuration. This
intentional break prevents a personal token from being used accidentally.

The backend resolves attribution as follows:

1. Resolve provider/login when both are supplied.
2. Exactly one ACTIVE account becomes the attribution user.
3. No binding uses the current namespace owner.
4. Disabled or ambiguous identity fails closed.
5. A new skill is owned by the attribution user.
6. Existing skill ownership is preserved; current attribution controls only the
   review submitter and human import attribution.

Namespace creation still uses the configured fixed fallback owner. Service
principals never appear in namespace membership, skill ownership, `created_by`,
or `review_task.submitted_by` user foreign keys.

Scanner, review, immutable versioning, idempotency, provenance, root routing,
and `/skillhub` routing remain unchanged.

## Importer And GitLab Stage

The Python importer reads `SKILLHUB_SERVICE_TOKEN` and sends it with the Bearer
scheme. Reports identify the authenticated service principal separately from the
resolved stable owner and review submitter. No pipeline user needs a personal
SkillHub token or SkillHub login session.

The reusable GitLab stage and Chinese SOP explain:

- how a Platform Admin creates the service principal and token;
- how to store the raw token as a masked/protected GitLab variable;
- how to map GitLab's triggering identity to Keycloak `preferred_username`;
- token expiry, rotation, revocation, and disabled-principal behavior;
- the required deployment/migration order;
- scanner/review expectations and troubleshooting.

## Error Handling And Security

- Token hashes and raw values are never logged.
- Authentication errors do not disclose whether a token id, hash, or principal exists.
- Service tokens cannot call token-management APIs or user/admin APIs.
- User tokens cannot call source-import APIs after cutover.
- Disabled principals and revoked/expired tokens fail before namespace or package mutation.
- Validation requests remain mutation-free apart from `last_used_at` and normal request audit.
- Token rotation is transactional and preserves the old token on failure.
- Concurrent token-name creation and rotation are protected by database uniqueness.
- Audit/provenance persistence remains in the same transaction as each source mutation.
- Existing scanner and namespace-owner authorization stay authoritative.

## Deployment And Compatibility

The schema migration is additive and safe to apply before the new backend. The
old backend ignores the new tables and nullable columns. Existing user tokens,
sessions, and historical import records require no migration.

Cutover order:

1. apply the Python-owned database migration;
2. deploy the backend and web changes;
3. create an ACTIVE `gitlab-oss-importer` principal as a Platform Admin;
4. create an expiring `source:import` service token;
5. store it as GitLab `SKILLHUB_SERVICE_TOKEN`;
6. remove the old `SKILLHUB_API_TOKEN` from the pipeline;
7. trigger a controlled import and complete normal review;
8. revoke the former user token if it is no longer needed elsewhere.

No new backend environment variable, network route, K8s workload, Redis key,
scanner configuration, or object-storage configuration is required.

## Verification

Unit and integration coverage must prove:

- service principal/token CRUD, validation, one-time secret, expiry, rotation,
  revocation, disable/enable, and concurrent uniqueness;
- ordinary user tokens and all existing token/device/account-merge tests remain unchanged;
- only service tokens with `source:import` reach source-import workflows;
- other APIs reject service tokens;
- exact preferred-username resolution, missing-binding fallback, and fail-closed
  disabled/ambiguous identities;
- service actor, attribution user, owner, submitter, creator, and audit fields are distinct;
- no service principal is stored in a user FK;
- admin UI hides raw tokens after the one-time dialog;
- importer requires `SKILLHUB_SERVICE_TOKEN` and rejects the legacy variable;
- root and `/skillhub` paths both work.

Final verification must run with PostgreSQL, Redis, MinIO, scanner, backend, and
both web/proxy variants. The smoke must create a service token through the normal
Platform Admin API, import through public Nginx, inspect database/audit/provenance,
approve through the normal review API, retry idempotently, rotate the token,
prove the old token fails, prove a user token fails, and import successfully with
the replacement token. Logs must contain no unhandled traceback, SQL syntax
error, or scanner task failure for the verified run.
